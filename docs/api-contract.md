# Petlo API contract — local v1

Status: implemented local single-user integration, 2026-10-20. The real backend is in `backend/`; API pages are enabled with `VITE_USE_API=true`. The original demo pages remain available when the flag is false/absent. Start with [local-full-stack-testing.md](local-full-stack-testing.md). No public backend deployment or production authentication is included.

## Transport conventions

- Base URL: `http://localhost:8000/api/v1` for an agreed local backend. Set `VITE_API_BASE_URL` to the full prefix; client endpoint functions add `/sessions` or `/jobs`.
- Resource IDs are opaque strings, even if the database uses integer keys. JSON keys use snake_case. Return resource objects directly, not an extra `data` envelope.
- Timestamps such as `recorded_at` and `date` use ISO 8601 with timezone. Event positions use real source-frame seconds, never frame number divided by average FPS.
- Rates are numbers from 0 to 1, or `null` when the denominator is zero. Unknown measurements are `null`, never fabricated zeroes.
- JSON requests use `application/json`. Video upload uses browser-generated `multipart/form-data`; do not manually set its Content-Type boundary.
- Errors use the envelope below. Do not return a successful HTTP status for an analysis/request failure.

```json
{
  "error": {
    "code": "VIDEO_INVALID",
    "message": "The uploaded file could not be decoded.",
    "details": null,
    "request_id": "request-123"
  }
}
```

Use 400 for invalid input, 401/403 for authentication/ownership failures, 404 for missing resources, 409 for conflicting session/job state, 413 for upload limits, 415 for unsupported media, 422 for unsupported analysis mode/input, and 500 for unexpected server errors. Error messages must not expose filesystem paths, SQL, or secrets. The client preserves `status`, `code`, `details`, and `requestId` in `ApiError`.

## Endpoints

### POST /sessions

Request:

```json
{"dog_id":"1","recorded_at":"2026-10-20T08:00:00Z"}
```

`dog_id` is required and must refer to an accessible dog. `recorded_at` is optional; the server supplies a timestamp when absent. Authenticated user identity comes from the server's authentication context, not a trusted `trainer_id` supplied by the browser. Return 201 with `SessionSummary`:

```json
{"session_id":"session-1","dog_id":"1","date":"2026-10-20T08:00:00Z","status":"draft","statistics":null}
```

### POST /sessions/{session_id}/videos

Multipart fields: `file` (one video) and `camera_perspective` (`front` or `side`). Multiple views are separate uploads attached to the same session. The initial contract allows at most one video per perspective; return 409 for a duplicate view. Reject uploads after analysis starts. Validate the actual media with the server's decoder; filename and browser MIME type are not proof of format. Storage keys are generated by the server.

Return 201 with `SessionVideo`:

```json
{"video_id":"video-1","session_id":"session-1","camera_perspective":"front","duration_sec":36.67,"width":3840,"height":2160,"playback_url":"https://media.example.invalid/video-1.mp4","preview_url":null}
```

Dimensions are orientation-normalized original dimensions. Metadata and playback URLs may be `null` while unavailable. Playback URLs must be absolute HTTPS in production (HTTP is allowed for local development), support normal browser playback/seeking, and must not be Windows paths. Signed URLs may be refreshed by refetching session details. `ready` means at least one valid source is available.

The current fetch upload helper reports completion, not byte-level upload percentage. Display an indeterminate upload indicator; never replace the existing demo timer with another fake real-upload percentage. Add XHR/upload progress or a signed object-storage upload flow later if measured upload progress is needed. Decide and document file-size/time limits on the backend before connecting large videos; frontend hosting does not itself receive the upload.

### POST /sessions/{session_id}/analysis

```json
{"video_ids":["video-1"],"mode":"single_view"}
```

Return 202 with `AnalysisJob`. Queue analysis outside the HTTP request. Reject concurrent active jobs for the same session with 409; never silently create a second job on a duplicate request. The client does not automatically retry POST requests.

- `single_view`: exactly one stored front/side tripod video; use its real source timestamps. The backend adapter runs the existing stages; general recognition quality on arbitrary inputs still needs evaluation.
- `sample_pair`: exactly two distinct uploaded videos, one front and one side. This mode is restricted to the already validated matching sample sources, verified by content hashes/provenance. Current `fuse_throw_events_v3.py` is bound to known filenames/video IDs and ordinal sample pairing. Do not rename arbitrary uploads to sample IDs or allow this mode for unrelated videos. Return 422 if unsupported.

```json
{"job_id":"job-1","session_id":"session-1","status":"queued","progress_percent":null,"stage":"queued","error":null}
```

### GET /jobs/{job_id}

Return 200 with the same job shape. Job states: `queued → running → completed | failed`. `progress_percent` is measured progress from 0–100 or `null` when unknown. `stage` is an English stage name or `null`.

```json
{"job_id":"job-1","session_id":"session-1","status":"failed","progress_percent":null,"stage":"decode","error":{"code":"VIDEO_DECODE_FAILED","message":"Video analysis failed during decoding."}}
```

Only mark completed after results and statistics are durably saved and retrievable. Polling stops on completed, failed, network/protocol error, unmount/job change, or the configurable waiting deadline (default 30 minutes). Browser abort stops requests/observation; it does not cancel server-side analysis. No server cancellation endpoint is defined yet. A failed job is a business outcome returned in the job object, distinct from an HTTP/request error.

### GET /sessions?page=1&page_size=20

Return 200: `{ "items": [SessionSummary], "page": 1, "page_size": 20, "total": 1 }`. Page starts at 1; page_size is 1–100. Return newest session dates first with a stable ID tiebreaker. History must fetch all relevant pages before calling its graph a complete history.

### GET /sessions/{session_id}

Return 200 with `SessionDetail`: all summary fields plus `videos: SessionVideo[]`, `events: SessionEvent[]`, `algorithm_version: string | null`, `limitations: string[]`, and `current_job_id: string | null`. Before completion, events are empty and statistics are `null`. Failed/new runs must not present stale results as that run's successful analysis.

Example event:

```json
{
  "event_id":"event-1",
  "category":"in_air_catch_candidate",
  "conflict":false,
  "source_intervals":[{"video_id":"video-1","start_sec":2.233,"end_sec":4.333}]
}
```

Every interval references a video in this session and satisfies `0 <= start_sec <= end_sec <= duration_sec`. Front/side times remain independent; seek using the selected video's interval, not a single shared time. Do not add interpolated/predicted positions as measured event evidence. Detailed tracks remain in algorithm artifacts and are not required in the initial page response.

## Statistics and algorithm mapping

Canonical categories match `cv/build_throw_statistics.py`:

| Existing outcome | API category |
| --- | --- |
| `catch_candidate`, fused `catch_success` | `in_air_catch_candidate` |
| `ground_pickup`, `ground_pickup_candidate` | `ground_pickup_candidate` |
| `miss`, `miss_candidate` | `miss_candidate` |
| `uncertain` | `uncertain` |

All counts remain unverified algorithm candidates. Do not interpret the internal name `catch_success` as confirmed human ground truth. Unknown outcome strings are errors, not automatically converted to a miss or catch.

`CandidateStatistics` contains:

```json
{
  "report_type":"unverified_candidate_statistics",
  "total_throw_candidates":4,
  "classified_candidate_events":4,
  "uncertain_events":0,
  "candidate_counts":{"in_air_catch_candidate":3,"ground_pickup_candidate":1,"miss_candidate":0,"uncertain":0},
  "candidate_coverage":1,
  "in_air_catch_candidate_rate":0.75,
  "retrieval_candidate_rate":1,
  "denominator_definition":"Classified throw candidates; uncertain outcomes are excluded. Ground pickups count as non-air catches in the in-air catch rate and as retrieved in the retrieval rate.",
  "human_labels_used_for_statistics":false
}
```

This is an example based on the existing sample, not a promised result for new uploads or an accuracy estimate. Classified = total - uncertain; airborne rate = airborne candidates / classified; retrieval rate = (airborne + pickup candidates) / classified; coverage = classified / total. Use `null` for any zero denominator. Physical distance, jump height, and real speed are unavailable without calibration and must not be populated from pixel trajectories.

## Frontend handoff

- Existing demo page files remain unchanged. Explicit API mode loads separate Live pages that use these helpers and the real local backend.
- Upload page: `createSession → uploadVideo` for each selected view `→ startAnalysis → useAnalysisJob`. Require a real dog selection/ID from the backend; never embed fake IDs.
- List/history: replace mock requests with `listSessions`. The old demo's flat `throw_count`, `catch_count`, and `catch_ratio` do not match the nested candidate statistics; map them explicitly and update UI labels/uncertain counts.
- Result page: replace hardcoded events and `/test_video.mp4` with `getSession`; render candidate categories and source-specific seek times. Account for null playback URLs and expired media URLs.
- Display English UI statuses/errors. A job with status failed has its own `job.error` message; `useAnalysisJob.error` is for request/polling errors. Render both.
- The local backend allows `http://localhost:5173` and `http://127.0.0.1:5173` by default and rejects non-loopback clients. Public Pages-to-backend integration requires a separately deployed authenticated HTTPS service. Authentication, cookies versus bearer tokens, and permissions must be agreed before real private-user integration. Cross-origin cookies would require explicit client credentials configuration plus backend CORS credentials support; that is not preconfigured here.
- `.env.local` and secrets stay local. VITE-prefixed settings are visible to every browser. Cloudflare Pages needs a reachable HTTPS backend URL at build time; localhost is only for local development.

Copy `.env.example` to `.env.local` and restart Vite after editing it. Also set `VITE_USE_API=true` to select the real API pages. No flag or `false` preserves demo mode.

## Local service additions

`GET /health` reports local service mode and configured maximum upload bytes. `GET /dogs` returns `{ "items": [{ "dog_id": "1", "name": "...", "breed": "...", "date_of_birth": "2020-01-01" }] }` for the configured local user. `POST /dogs` accepts name, breed and date_of_birth and returns a new stored dog record with status 201. This is local development ownership, not login authentication.

`GET /videos/{video_id}/playback` serves the generated H.264 source-time preview with byte Range support (206). Before successful analysis, playback_url/preview_url are null; the original HEVC file is not assumed to be browser playable. The configured upload limit defaults to 1024 MiB per file. Multipart overhead has a separate small allowance; actual file bytes are also checked. Backend errors and source filenames never expose an arbitrary filesystem read endpoint.

The job runner uses one local executor and records queued/running/completed/failed states in the database. It saves results transactionally. On service restart, interrupted active jobs become failed with SERVER_RESTARTED; no automatic job replay is attempted. Generated evidence stays per job. MySQL extension tables are additive; default development uses SQLite.

## Local demonstration additions (2026-10-21)

Job responses additionally include persisted `created_at` and nullable `finished_at` timestamps, in UTC ISO 8601 format. Elapsed time includes queue waiting, and freezes at `finished_at` for completed/failed jobs. A successful GET is a status-check timestamp, not an inference heartbeat. Polling/reloading does not enqueue work. The API remains loopback-only; no database migration is needed for these already persisted columns.

The frontend task route `/sessions/:id/analysis` restores `current_job_id` from the session endpoint. Local report JSON includes session identity, algorithm version, limitations, candidate statistics and per-view event intervals; event CSV has one row per event/view, with `human_verified=false`. Downloads do not change machine predictions or supply human labels to inference.
